# 0005. 选择前后端分离架构

- 状态: 已采纳
- 日期: 2026-07-28

## 背景

需要开发 VocabMaster - 跨平台英语单词学习助手，核心功能包括：
- 用户注册/登录
- 选择词库
- 学习单词（拼写/音标/释义/例句）
- 标记掌握状态
- 追踪学习进度

需要支持的平台：Windows 桌面 → Mac → 移动端 → 网页版

## 决策

采用 **前后端分离架构**：

- **前端**：React 18 + TypeScript + Vite + Tailwind + Tauri 2
  - 负责所有 UI 和业务逻辑编排
  - 状态管理用 Zustand
  - 平台适配用 adapters 层隔离 web/tauri 差异

- **后端**：Python 3.10+ + FastAPI + SQLAlchemy + SQLite
  - 提供用户认证 API（JWT）
  - 提供词库管理 API
  - 提供学习进度 API
  - 数据持久化

- **通信**：前端通过 HTTP 调用后端 RESTful API

## 理由

### 为什么选择前后端分离

1. **职责清晰**：前端专注 UI/UX，后端专注数据和业务规则
2. **独立开发**：前后端可并行开发，互不阻塞
3. **易于测试**：前端 mock API，后端使用内存数据库，测试边界清晰
4. **易于扩展**：后续可独立部署、独立扩容

### 为什么选择 Python FastAPI

1. **AI 时代最佳选择**：与 AI 框架（LangChain、LlamaIndex）无缝集成，未来可扩展智能推荐功能
2. **性能优秀**：基于 Starlette 和 Pydantic，性能接近 Node.js
3. **类型提示**：自动生成 API 文档（OpenAPI/Swagger），减少文档维护成本
4. **学习曲线平缓**：Python 语法简单，团队易上手
5. **生态成熟**：SQLAlchemy（ORM）、pytest（测试）、Pydantic（验证）都很成熟

### 为什么选择 Tauri（桌面壳）

1. **体积小**：打包后仅几 MB，远小于 Electron（100MB+）
2. **性能好**：Rust 后端，内存占用低
3. **安全**：Rust 的内存安全保证
4. **跨平台**：一套代码支持 Windows/Mac/Linux

### 为什么前后端分离适合本项目

| 方案 | 优点 | 缺点 | 是否适合 |
|---|---|---|---|
| 前后端分离 | 职责清晰、易测试、易扩展 | 需维护两套代码 | ✅ 适合（需要用户认证、数据持久化） |
| 纯前端（无后端） | 零运维、部署简单 | 无法做用户认证、数据不安全 | ❌ 不适合（需要用户系统） |
| Monolith（前后端一体） | 部署简单 | 测试困难、扩展性差 | ❌ 不适合（目标是跨平台） |

## 后果

### 正面

- ✅ **架构清晰**：前端、后端、数据库三层，职责明确
- ✅ **易于测试**：前端 mock API，后端使用内存数据库
- ✅ **易于扩展**：可独立部署，可迁移到 PostgreSQL
- ✅ **AI 友好**：Python 后端未来可集成 AI 能力

### 需要注意

- ⚠️ **需维护两套代码**：前端 TS + 后端 Python
- ⚠️ **需 API 文档**：FastAPI 自动生成文档，但需要维护请求/响应示例
- ⚠️ **CORS 配置**：需要正确配置跨域访问
- ⚠️ **认证管理**：JWT token 需要妥善管理（刷新、过期）

### 测试策略

- **前端测试边界**：mock `adapters/apiFetch`，隔离 HTTP 调用
- **后端测试边界**：使用 `sqlite:///:memory:` 内存数据库
- **E2E 测试**：Playwright 覆盖核心用户流程
