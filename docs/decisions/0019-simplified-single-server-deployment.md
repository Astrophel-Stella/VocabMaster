# ADR-0019: 简化部署方案 - 单服务器架构

## 状态
已采纳 (2026-07-31)

> ℹ️ 本 ADR 的**单服务器部署方案**（本机开发 + 单台线上服务器 + 冒烟测试 + 自动回滚）依然有效。
> 但文中"架构师审核 → 架构师批准后自动合并"的**角色/合并**表述已被 ADR-0020 取代：
> 合并批准权在**人类审核者**（AI 只做 advisory 预审）。请以 ADR-0020 为准。

## 背景

用户环境限制：
- 本机开发环境
- 一台线上服务器 (111.229.214.179)
- 无staging环境

需要适配的国外最佳实践：
- **GitHub Flow**: 简化分支策略
- **GitOps**: 以Git为源的部署
- **Continuous Delivery**: 自动化交付

## 决策

### 1. 简化的环境模型

```
┌─────────────┐         ┌─────────────┐
│ 本机开发环境 │  push   │   GitHub    │
│ (localhost)  ├────────►│  (代码仓库)  │
└─────────────┘         └──────┬──────┘
                               │ merge to master
                               │
                        ┌──────▼──────┐
                        │ GitHub Actions│
                        │ (自动化构建)  │
                        └──────┬──────┘
                               │ SSH deploy
                        ┌──────▼──────┐
                        │ 线上服务器    │
                        │111.229.214.179│
                        └─────────────┘
```

### 2. 简化的流水线

```yaml
阶段1: 质量门禁 (GitHub Actions自动执行)
  ├─ Lint检查
  ├─ 单元测试
  ├─ 集成测试
  └─ E2E测试

阶段2: 架构师审核 (自动通知)
  └─ 架构师批准后自动合并

阶段3: 部署确认 (唯一人工闸口)
  └─ 用户在Issue回复"确认上线"

阶段4: 自动部署 (GitHub Actions自动执行)
  ├─ 构建Docker镜像
  ├─ SSH到线上服务器
  ├─ 拉取最新代码
  ├─ 重新构建部署
  └─ 冒烟测试验证
```

### 3. 部署策略

**策略**: 直接部署到生产环境

**前提条件**:
- 所有测试通过 (单元+集成+E2E)
- 架构师审核通过
- 用户明确确认

**回滚方案**:
- 自动回滚: 冒烟测试失败时自动回滚到上一版本
- 手动回滚: `git reset --hard HEAD~1` + 重新部署

### 4. 与完整方案的区别

| 方面 | 完整方案 (多环境) | 简化方案 (单服务器) |
|------|-------------------|---------------------|
| 环境数量 | 3个 (dev/staging/prod) | 2个 (本机/prod) |
| Staging测试 | ✅ 有 | ❌ 无 |
| 生产部署 | 灰度发布 | 直接部署 |
| 回滚方式 | 自动+手动 | 自动+手动 |
| 风险等级 | 低 | 中等 |

### 5. 风险缓解措施

**替代Staging的方案**:
1. **强化E2E测试**: 在本机环境运行完整E2E，模拟生产配置
2. **生产冒烟测试**: 部署后立即验证核心功能
3. **自动回滚**: 冒烟测试失败自动回滚
4. **Feature Flags**: (可选) 隐藏新功能，验证后再开放

**E2E测试增强**:
```yaml
# 在本机运行生产配置的E2E测试
- 使用生产环境配置
- 使用真实数据库schema
- 模拟真实用户场景
- 覆盖所有核心路径
```

## 实施方案

### 1. 修改GitHub Actions流水线

去掉staging相关步骤，简化为：
- 质量门禁 → 架构师审核 → 用户确认 → 直接部署生产

### 2. 创建生产配置文件

```bash
# .env.production
VITE_API_URL=  # 空，使用相对路径
```

### 3. 创建部署脚本

```bash
#!/bin/bash
# scripts/deploy.sh
# 一键部署脚本
```

### 4. 配置GitHub Secrets

只需要3个secrets:
- `SSH_PRIVATE_KEY`: SSH私钥
- `PROD_HOST`: 111.229.214.179
- `PROD_USER`: root

## 后果

### 正面
- 简单易维护，适合小团队
- 成本低（无需额外服务器）
- 仍然保持自动化和高质量

### 负面
- 无staging环境，风险稍高
- 需要更严格的测试覆盖
- 部署失败影响面较大

### 缓解措施
- 强化E2E测试覆盖
- 自动回滚机制
- 部署前人工确认
