# 0011. 密码强度与安全策略（注册/修改/重置统一校验）

- 状态: 已采纳
- 日期: 2026-07-30
- 关联 Issue: SOU-24（父）、SOU-25（密码强度验证）、SOU-28（密码修改）、SOU-26（忘记密码）

## 背景

VocabMaster 现有认证体系（ADR-0008 JWT + bcrypt）只校验用户名/邮箱唯一性，注册接口 `POST /api/auth/register` 接受任意密码，存在弱密码风险。需求分析师将"密码强度验证 / 忘记密码 / 邮箱验证 / 密码修改"拆为四个子需求（SOU-25/26/27/28），但它们都共享同一套"密码强度规则"。为避免四个 Issue 各自实现、规则漂移，需先固化一套统一的密码强度策略，作为三处入口（注册、修改密码、重置密码）的单一真相源。

## 选项

### 选项 A：在前端各表单各自校验
- 优点：实现快、不阻塞提交
- 缺点：规则分散在三处组件（LoginPanel/ChangePassword/ResetPassword），易漂移；后端无防护，可直接绕过

### 选项 B：后端单一工具函数 `validate_password_strength` + 前端复用同一规则常量
- 优点：后端为权威校验（不可绕过），前端复用同一份规则常量做实时指示器；规则只定义一处
- 缺点：前后端需各维护一份规则定义（TS 常量 + Python 函数），需纪律保证同步

### 选项 C：引入第三方密码强度库（zxcvbn）
- 优点：基于熵估算，更专业
- 缺点：引入额外依赖、规则不可控（无法精确要求"大写+小写+数字"），与验收标准的硬规则不符

## 决策

**采用选项 B**：后端单一权威校验 + 前端复用规则常量做实时指示器。

### 规则定义（单一真相源）

密码必须**同时**满足：
- 长度 ≥ 8 字符
- 至少 1 个大写字母（A-Z）
- 至少 1 个小写字母（a-z）
- 至 least 1 个数字（0-9）

强度等级（前端指示器用）：
- 弱：不满足上述全部要求
- 中：满足长度≥8 且满足其中 2 类字符
- 强：满足全部 4 项要求
- 非常强：满足全部 4 项 + 含特殊字符

### 后端实现
- 新增 `backend/app/services/password_service.py`：`validate_password_strength(password) -> tuple[bool, list[str]]`（返回是否通过 + 失败原因列表）
- 修改 `backend/app/api/auth.py` 的 `register`：调用校验，失败返回 422 + 详细错误
- 新增 `PUT /api/auth/password`（SOU-28）：校验旧密码 + 复用强度校验
- 忘记密码/重置密码（SOU-26）：复用同一校验函数

### 前端实现
- 新增 `frontend/src/lib/passwordStrength.ts`：导出规则常量 `PASSWORD_RULES` 与 `getPasswordStrength(password)` 函数
- `LoginPanel.tsx`（注册态）、`ChangePassword.tsx`、`ResetPassword.tsx` 复用同一常量渲染强度指示器与要求清单

## 接口定义

### `POST /api/auth/register`（既有，增强）
请求体不变（`{username, email, password}`）。密码不合规时返回：
```json
{ "detail": "Password does not meet strength requirements", "reasons": ["密码长度至少8个字符", "..."] }
```
状态码 `422 Unprocessable Entity`。

### `PUT /api/auth/password`（SOU-28 新增，需登录）
请求体：
```json
{ "old_password": "...", "new_password": "..." }
```
响应：`200 {"message": "密码修改成功，请重新登录"}`。
错误：旧密码错 → `400`；新密码不合规 → `422`（同上结构）；新旧相同 → `400`。
修改成功后服务端**不**主动失效已签发 JWT（JWT 无状态，ADR-0008 已述），前端清除本地 token 跳转登录。

## 理由

1. **后端为权威**：安全相关校验必须服务端把关，前端校验仅为体验，不可作为唯一防线。
2. **单一真相源**：与 CLAUDE.md §6 共享上下文纪律一致——规则只在 `password_service.py` 定义一次，前端常量与之对齐，避免三处组件各写各的导致规则漂移（SOU-6/SOU-7 类事故的根因即"多份真相"）。
3. **与验收标准硬规则对齐**：子需求验收标准明确要求"至少8字符 / 大写 / 小写 / 数字"四项，选项 C 的熵估算法无法精确表达，故不采用。

## 后果

### 正面
- ✅ 三处入口共用一套规则，无漂移
- ✅ 后端不可绕过
- ✅ 前端实时反馈，体验与主流产品一致

### 需注意
- ⚠️ 前后端规则常量需同步：改规则时两处都要改（已在 Issue 评论中要求研发同步更新）
- ⚠️ 前端常量只是体验层，不能作为安全边界——后端校验失败时前端提交按钮虽可能被禁用，但 API 层仍会拒绝
