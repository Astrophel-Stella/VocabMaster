## 背景

SOU-25（密码强度验证 / REQ-AUTH-006）交付复盘发现流水线存在多处偏差，根因是各环节强制规则未在 AI 共享指令（`CLAUDE.md`）与流程文档（`docs/build.md`）中显式固化，各角色 agent 各自执行时出现缺环：

1. **未合并 master 即部署**：代码虽从 master 切出（`merge-base = 06e3ed5` = 远端 master HEAD），但功能测试通过后 PR #19 仍 OPEN、未合并，部署助手直接从特性分支 `agent/ui/4f164100`（`32279aa`）Docker 构建上线。生产基线（`32279aa`）超前于 master（`06e3ed5`），**基线不一致**。
2. **UI 功能自动化测试（Playwright E2E）被跳过**：仓库已有 E2E 套件（`frontend/e2e/web/`，PR #16，OPEN 未合并）且其覆盖范围为 REQ-UI-001 / REQ-AUTH-001~005，**不含 REQ-AUTH-006**。本次功能测试仅做 Vitest 组件单测 + HTTP 接口集成，**无任何浏览器级用例**覆盖密码强度指示器的真实交互。
3. **测试与文档未"跟随工程"**：测试用例（`test_auth.py`、`LoginPanel.test.tsx`，均标 `REQ-AUTH-006`）与新增需求锚点（PR #18 的 `requirements.md` REQ-AUTH-006~009、ADR 0011~0014）都停留在特性分支未进 master，下次拉 master 跑回归时这些资产并不存在。

## 决策

固化「北极星蓝图」交付流水线，作为**所有需求交付的强制基线**，顺序不可打乱：

```
① 从 origin/master 拉取代码 → 切特性分支修改
② 全部测试通过：代码级单测（Vitest/pytest）+ 集成测试 + UI 功能自动化 E2E（Playwright）
③ 架构师审核 PR（对照验收标准 + ADR + 接口定义）
④ 合并 master（由架构师执行 `gh pr merge`）
⑤ 等待人工（陈豪 / QA）确认部署上线
⑥ 基于 master 构建 → 部署 → 回归测试
```

### 四条硬规则

1. **master 起步**：所有修改从 `origin/master` 切特性分支，不在特性分支上叠特性分支；PR 目标分支恒为 `master`。
2. **测试全过含 E2E**：面向用户的功能，必须同时有代码级单测**和**浏览器级 E2E（Playwright，模拟人在浏览器操作）。E2E **不可跳过、不可用接口测试或组件单测替代**。无 E2E 覆盖的功能不得将需求状态升到「✅ 已验收」，不得进入部署环节。
3. **测试与文档跟随工程**：测试用例、需求规格（`specs/requirements.md` 锚点）、ADR（`docs/decisions/`）随代码同 PR 提交、同 PR 合并 master；**不单次使用、不留特性分支**。回归测试直接拉 master 复用全部历史用例。
4. **合并前置部署**：部署必须在 PR 合并 master **之后**、基于 master 构建；**特性分支不直接上线**。架构师审核通过后**由架构师执行 `gh pr merge` 合并 master**（不再 @mention 人工 owner）；人工（QA/陈豪）确认后再部署。

## 理由

- **基线一致**：部署基于 master，保证生产代码 = 仓库主线代码，可追溯、可回滚，杜绝"生产跑的代码 master 里没有"。
- **E2E 不可替代**：组件单测验证逻辑、接口测试验证契约，但真实浏览器交互（如注册页输入密码、观察强度条与要求清单实时勾选）只有 E2E 能覆盖。SOU-25 的覆盖缺口正是缺这一层。
- **资产沉淀**：测试与文档随工程版本化，下次回归直接拉 master 复用，而非消失在未合并的特性分支里。
- **人工闸口**：部署是不可逆的对外动作，由 QA/陈豪把关，AI 不越权自行部署。**合并 master 属架构师职责**（架构师审核通过即合并，不占人工闸口）。

## 接口定义（流程契约）

| 环节 | 责任角色 | 入口条件 | 出口条件（DoD） |
|---|---|---|---|
| ① 切分支 | 研发工程师 | 需求 Issue + ADR + 验收标准 | 分支基于 `origin/master` HEAD |
| ② 测试 | 单元&集成测试工程师 + UI&功能自动化测试工程师 | 研发实现完成 | 单测+集成+E2E 全绿；用例标 `REQ-ID` |
| ③ 审核 | 项目管理&架构师 | 测试全绿 | PR 满足验收标准 + ADR + 接口定义 |
| ④ 合并 | 项目管理&架构师 | 架构师审核通过 | PR 合入 `master`（架构师执行 `gh pr merge`） |
| ⑤ 部署确认 | 人工（QA） | master 已更新 | 人工确认上线 |
| ⑥ 构建部署回归 | 构建助手 + 部署助手 | 人工确认 | 基于 master 构建；回归通过 |

> Bug 验证路由仍遵守既有规则：Bug 由谁发现，修复后就由谁验证——不交叉指派（代码级→单元&集成测试工程师，功能级→UI&功能测试工程师）。

## 后果

- 每个面向用户的功能交付成本上升（必须补 E2E），但回归复用价值与缺陷拦截率提升，避免"SOU-25 式"浏览器交互零覆盖。
- 架构师新增「审核 PR + **合并 master**」职责环节（合并由架构师执行，非人工 owner）；部署助手改为**基于 master** 构建，不再从特性分支直接上线。

  - PR #19（密码强度功能代码 + 单测）：审核通过后合并。
  - 此后 sou-25 的部署应基于合并后的 master 重新构建。
